# Review Assistance

Версия 0.8.5 открывает учебный MR, локальные изменения Git и ревью из GitLab или GitHub по ссылке.

## Запуск

В рабочей папке проекта выполните `npm run start:dev`. Nest CLI пересобирает TypeScript и перезапускает Electron после успешной компиляции. Команда `npm run dev` запускает тот же режим. На этом Mac уже подготовлена локальная копия Electron в `.local/`. Учебный MR читается с диска.

Для нового checkout сначала установите зависимости и Electron.

```bash
npm ci
npm install --no-save electron@40.10.3
npm run start:dev
```

| Команда | Что делает |
| --- | --- |
| `npm run build` | Собирает TypeScript в `dist/` через Nest CLI. |
| `npm start` | Собирает проект и один раз запускает Electron. |
| `npm run start:dev` | Следит за TypeScript, пересобирает проект и перезапускает Electron. |
| `npm run start:debug` | Запускает режим разработки с отладчиком основного процесса Electron на `127.0.0.1:9229`. |
| `npm run start:prod` | Запускает Electron из готовой сборки после `npm run build`. |

Nest CLI запускает небольшой адаптер, который открывает проект в Electron. Electron загружает общий вход `src/main.ts` из сборки. [Конфигурация Nest CLI](nest-cli.json) · [Адаптер запуска](src/desktop/launch.ts)

## Проверка

1. Нажмите **Открыть пример**. Слева появятся группы **Основное**, **Тесты**, **Только оформление и комментарии** и **Остальное**. Справа откроется diff контроллера.
2. Откройте `delivery.ts` и найдите замену `>` на `>=` в условии бесплатной доставки. В группе **Тесты** откройте `delivery.test.ts` с проверкой суммы ровно на пороге.
3. Раскройте **Только оформление и комментарии**. У `labels.json` указано **Только форматирование JSON**, а у `states.ts` — **Правки обычных комментариев**. Нажмите на любой из них, чтобы открыть исходный diff.
4. В группе **Основное** найдите директиву линтера в `audit.ts`. Изменение числа в `checkout.json` и файл `checkout.rules` видны в группе **Остальное** с пояснениями.
5. Раскройте **Остальное** и откройте `manual.md`. Расширение `.md` определяет эту группу, хотя файл находится в `tests/`.

Если `fixtures/example.json` недоступен или повреждён, приложение показывает ошибку. После восстановления файла можно повторить открытие без перезапуска.

## Расширение блока 1 «Сценарий ревью»

Блок 1 выполнен. Приложение открывает учебное ревью, показывает список файлов и diff. Задачи ниже расширяют этот сценарий и остаются к реализации.

### 1.1. Фильтры перед построением цепочки

Сейчас фильтры определяют группы в списке. Очередь **Дальше** включает и файлы из **Остального**. Применить фильтры перед построением основной цепочки. Исключить из неё файлы, которые явно не относятся к языкам программирования. Оставить их в списке для ручного открытия diff.

**Проверка.** Открыть ревью с изменениями в `service.go`, `service_test.go`, `config.yaml`, `README.md` и `profile.heap`. Последовательные нажатия **Дальше** проходят по коду и тесту. Конфиг, документация и профиль доступны в **Остальном**. Если ревью состоит только из исключённых файлов, **Дальше** недоступна, а diff любого файла можно открыть из списка.

### 1.2. Группировка по модулям и каталогам

Сейчас список в ревью по ссылке разделяет основной код и тесты. После фильтрации сгруппировать файлы по принадлежности к модулю. Внутри модуля учитывать близость каталогов, чтобы ревьюер проходил связанные изменения вместе. Использовать один порядок для списка файлов в основной цепочке и кнопки **Дальше**. Тест рядом с реализацией оставить рядом. Отдельное дерево тестов показать на его месте в структуре проекта с сохранением вложенности каталогов.

**Проверка.** Открыть подставное ревью с перемешанными файлами из `src/orders/api/`, `src/orders/service/` и `src/payments/`. Файлы каждого модуля идут подряд. `src/orders/service/order.test.ts` находится рядом с реализацией, а `tests/integration/orders/order.spec.ts` виден в ветке `tests/integration/orders/`. Обход через **Дальше** совпадает с порядком файлов в основной цепочке списка. Каждый файл в цепочке встречается один раз.

### 1.3. Короткий ИИ-обзор MR/PR

В текущем приложении автоматической сводки нет. При открытии MR или PR запускать короткий обзор, если ИИ-агент настроен и его ключ подключён. В сводке объяснить, какие возможности добавлены, что исправлено или как изменилось поведение. Использовать изменения тестов вместе с изменениями реализации, чтобы извлечь важные условия и ожидаемые результаты. По одному добавленному тесту нельзя заключить, что появилась новая функция.

**Проверка.** С подставным агентом открыть MR и PR, в которых реализация меняет порог, а тест проверяет граничное значение. Обзор отражает новое поведение и граничный случай. В отдельном ревью изменён только тест. Обзор описывает добавленную проверку без утверждения о новой возможности.

### 1.4. Хранение ключа ИИ-агента

Использовать тот же механизм защищённого хранения, что и для GitHub и GitLab. Сохранять ключ агента в отдельной записи Связки ключей macOS. Ключ нельзя помещать в исходный код или репозиторий.

**Проверка.** Подключить подставной ключ и перезапустить приложение. Запись агента сохраняется отдельно от записей GitHub и GitLab. Удаление подключения агента не влияет на Git-подключения. Подставной ключ отсутствует в исходниках и файлах репозитория.

### 1.5. Загрузка обзора и ревью без ИИ

Пока агент формирует сводку, показывать индикатор загрузки в области обзора. Список файлов, diff и кнопка **Дальше** доступны с момента открытия ревью. Если агент не настроен или ключ не подключён, сразу открыть обычное ревью с фильтрацией, группировкой и сортировкой.

**Проверка.** Открыть MR/PR с подставным агентом, который отвечает с задержкой. В области обзора виден индикатор. Пока он виден, можно открыть diff и перейти к следующему файлу. После ответа на месте индикатора появляется сводка. Повторить проверку без настроенного агента и с настроенным агентом без ключа. В обоих случаях ревью открывается сразу, индикатор не появляется и запрос к агенту не отправляется.

## Подключение GitLab

1. В GitLab создайте legacy Personal Access Token с правом `read_api` или fine-grained токен с правами **User → User → Read** и **Merge Request → Read** для проекта из ссылки на MR. [Права GitLab REST API](https://docs.gitlab.com/auth/tokens/fine_grained_access_tokens_rest/)
2. В приложении нажмите **GitLab**. В поле **Адрес сервиса** введите основной HTTPS-адрес вашей установки, например `https://gitlab.example.com`, и токен. При необходимости включите VPN.
3. Нажмите **Подключить**. Приложение проверит токен через `/api/v4/user` и покажет имя пользователя.
4. Перезапустите приложение и снова откройте **GitLab**, чтобы проверить сохранение.
5. Нажмите **Отключить**, чтобы удалить токен из Связки ключей. Для замены токена введите новый и нажмите **Обновить подключение**.

В поле **Ссылка на ревью** вставьте ссылку на MR с подключённого GitLab и нажмите **Открыть**. Выберите файл слева, чтобы увидеть diff. Приложение показывает предупреждение о неполных данных, когда GitLab сообщил об ограничении или вернул неполный diff. [GitLab Merge Requests API](https://docs.gitlab.com/api/merge_requests/#list-merge-request-diffs)

Токен хранится как пароль в Связке ключей macOS. Основной процесс отправляет его на указанный HTTPS-адрес, а при перенаправлении останавливается. Если сохранить токен не удалось, кнопка **Только до выхода** позволяет держать его в памяти. Интерфейс показывает, какой режим действует.

Для сборки локального помощника Связки ключей на macOS используются Xcode Command Line Tools. Приложение собирает его при запуске и сохраняет в `.local/bin/`.

## Подключение GitHub

1. Создайте **Fine-grained personal access token**. Выберите тестовый репозиторий и установите **Pull requests → Read-only**. [Права GitHub API](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files)
2. Нажмите **GitHub**, введите токен и нажмите **Подключить**. Приложение покажет имя пользователя.
3. В том же окне GitHub вставьте ссылку вида `https://github.com/owner/repo/pull/123` и нажмите **Открыть**. Поле видно до подключения. Выберите файл, чтобы увидеть diff.
4. При неполных данных приложение показывает предупреждение. Файлы, для которых GitHub не вернул текстовый diff, видны в списке.

GitHub-токен хранится в отдельной записи Связки ключей `local.review-assistance.github`. Кнопка **Отключить** удаляет эту запись. Режим **Только до выхода** хранит токен в памяти. Запросы с токеном GitHub идут на `https://api.github.com`.

## Группировка файлов

`md`, `txt`, `png`, `jpg`, `jpeg`, `tiff`, `log`, `pdf`, `bak`, `cpu` и `heap` попадают в **Остальное** по расширению. Из остальных файлов те, в чьём пути есть подстрока `spec` или `test`, попадают в **Тесты**. Регистр букв не влияет на совпадение. **Основное** и **Тесты** раскрыты при открытии ревью. **Остальное** и **Только оформление и комментарии** свёрнуты.

Для оставшихся файлов фильтр сравнивает разобранные токены JSON и синтаксис JavaScript и TypeScript. Обычные комментарии проверяются отдельно от кода. Для JavaScript и TypeScript нужен diff с достаточным контекстом от начала файла. Директивы инструментов и сомнительные изменения проходят к следующим правилам группировки.

Фильтры подключаются в одном модуле. Они возвращают результат проверки и причину. Экран решает, в каком списке показать файл. [Модуль фильтров](src/review/review-filters.module.ts) · [Контракт фильтра](src/review/domain/file-filter.ts)

Команда `npm test` проверяет правила и подключает дополнительный фильтр в тесте.

## Блок 4а «Языки файлов»

GitLab MR, GitHub PR, локальный Git и учебный пример используют один фильтр. Он читает каталог [GitHub Linguist](https://github.com/github-linguist/linguist/blob/v9.5.0/lib/linguist/languages.yml) из закреплённого npm-пакета `linguist-languages`. Классификация идёт по имени и расширению изменённого файла. Если расширение соответствует нескольким языкам, достаточно одного кандидата типа `programming`. Анализ содержимого движком Linguist и чтение `.gitattributes` в этот режим не входят.

Первое подходящее правило определяет группу:

1. Файлы с перечисленными выше специальными расширениями идут в **Остальное**.
2. Тесты по пути идут в **Тесты**.
3. Подтверждённые правки только оформления или обычных комментариев идут в **Только оформление и комментарии**.
4. Файлы на языках типа `programming` идут в **Основное**.
5. Остальные файлы, включая разметку и неизвестные форматы, идут в **Остальное** с пояснением.

Приложение определяет типы изменённых файлов без запросов списка языков и без кэша статистики проекта. Дополнительное право `Project: Read` для классификации не требуется. Язык нового файла оценивается по тем же правилам, что и язык остальных изменённых файлов.

## Блок 5 «Порядок чтения»

Откройте пример. Нажмите **Дальше** три раза, чтобы пройти от `delivery.controller.ts` через `delivery.ts` и `delivery.repository.ts` к `delivery.test.ts`. Рядом с кнопкой видна позиция в очереди. На последнем файле кнопка выключается.

Очередь строится локально по путям и относительным импортам JavaScript и TypeScript, видимым в diff. В ревью по ссылке **Дальше** идёт по списку слева сверху вниз. Сначала идут все файлы из **Основного**, затем **Тесты**, затем остальные группы. Порядок внутри группы учитывает найденные связи между файлами. Каждый файл входит в очередь один раз. Можно выбрать любой файл слева и продолжить с него.

## Блок 6 «Прогресс»

Нажмите на имя файла над diff, чтобы свернуть или развернуть его. Галочка **Просмотрен** сворачивает diff и добавляет отметку слева. Снятие галочки разворачивает diff. Выберите другой файл и вернитесь к первому, чтобы увидеть **×2**. Повторный клик по открытому файлу и прокрутка счётчик не меняют.

При возврате к просмотренному файлу его diff открывается свёрнутым. При повторном открытии того же ревью приложение восстановит последний файл без прибавления к счётчику. Отметки и счётчики хранятся в локальном профиле отдельно для каждого ревью. Если diff изменился, отметка этого файла сбросится, а счётчик сохранится.

## Блок 7 «Локальный Git»

Установите Git, если он ещё недоступен. Нажмите **Открыть папку** и выберите рабочее дерево Git или папку внутри него. Приложение покажет итоговые изменения относительно `HEAD`, включая подготовленные, неподготовленные и новые неигнорируемые файлы. В репозитории без коммитов сравнение идёт с пустым деревом.

Для локальной папки действуют обычные группы файлов, кнопка **Дальше** и локальный прогресс. Бинарные файлы видны в списке с пояснением. Приложение читает рабочее дерево и индекс без сетевого подключения. Повторно откройте папку, чтобы увидеть свежий diff.

## Логи

При запуске через `npm run start:dev` логи появляются в том же терминале. В них видны запуск и закрытие окна, подключения, операции со Связкой ключей, загрузка MR и PR, страницы diff и ошибки. Для запросов указываются сервис, операция, HTTP-статус и время. Для сетевых ошибок по возможности указывается код причины. При отказе GitLab в доступе к профилю или MR приложение отдельно распознаёт известный код нехватки прав и HTML-ответ. Код 429 означает ограничение частоты запросов.

Чтобы увидеть распознанные языки и форматы изменённых файлов, запусти `REVIEW_ASSISTANCE_DEBUG=1 npm run start:dev` и открой ревью. В терминале появится строка вида `[Linguist] detectedLanguages=["Go","TypeScript","YAML"]`.

Токены, ссылки, имена аккаунтов, пути к файлам из ревью и содержимое diff в эти логи не записываются.

## Архитектура

NestJS работает внутри основного процесса Electron. Общая точка входа запускает и закрывает контекст. AppModule подключает модули окна и ревью и регистрирует адаптер между ними. [main.ts](src/main.ts) · [AppModule](src/app.module.ts)

- DesktopModule управляет окном Electron. AppModule передаёт ему пути к странице и preload. [DesktopModule](src/desktop/desktop.module.ts)
- ReviewModule связывает прикладной сервис с источником данных через интерфейс. Адаптер источника читает локальный JSON и разбирает unified diff. [ReviewModule](src/review/review.module.ts) · [Прикладной сервис](src/review/application/open-example-review.ts) · [Адаптер источника](src/review/infrastructure/json-example-review.source.ts)
- Домен описывает MR, файлы и строки diff. Он проверяет уникальность путей и наличие изменений, подсчитывает добавленные и удалённые строки. [Домен ревью](src/review/domain/review.ts)
- Слой представления отображает diff. Кнопка «Открыть пример» отправляет запрос через preload. Адаптер IPC проверяет, что запрос пришёл из основного окна, и вызывает прикладной сервис. [Код представления](src/presentation/review/) · [Обработчик IPC](src/presentation/review/review-ipc.handler.ts)
- Модули GitLab и GitHub используют общий сервис подключения и отдельные записи Связки ключей. Каждый модуль подключает свой адаптер загрузки ревью. [GitLabModule](src/gitlab/gitlab.module.ts) · [GitHubModule](src/github/github.module.ts)
