# Review Assistance

Версия 0.6.7 открывает учебный MR и ревью из GitLab или GitHub по ссылке. Кнопка **Дальше** ведёт по очереди чтения файлов.

## Запуск

В рабочей папке проекта выполните `npm run start:dev`. Nest CLI пересобирает TypeScript и перезапускает Electron после успешной компиляции. Команда `npm run dev` запускает тот же режим. На этом Mac уже подготовлена локальная копия Electron в `.local/`. Учебный MR читается с диска.

Для нового checkout сначала установите зависимости и Electron.

```bash
npm ci
npm install --no-save electron@40.10.3
npm run start:dev
```

| Команда | Что делает |
| --- | --- |
| `npm run build` | Собирает TypeScript в `dist/` через Nest CLI. |
| `npm start` | Собирает проект и один раз запускает Electron. |
| `npm run start:dev` | Следит за TypeScript, пересобирает проект и перезапускает Electron. |
| `npm run start:debug` | Запускает режим разработки с отладчиком основного процесса Electron на `127.0.0.1:9229`. |
| `npm run start:prod` | Запускает Electron из готовой сборки после `npm run build`. |

Nest CLI запускает небольшой адаптер, который открывает проект в Electron. Electron загружает общий вход `src/main.ts` из сборки. [Конфигурация Nest CLI](nest-cli.json) · [Адаптер запуска](src/desktop/launch.ts)

## Проверка

1. Нажмите **Открыть пример**. Слева появятся группы **К просмотру**, **Тесты**, **Только оформление и комментарии** и **Прочее**. Справа откроется diff контроллера.
2. Откройте `delivery.ts` и найдите замену `>` на `>=` в условии бесплатной доставки. В группе **Тесты** откройте `delivery.test.ts` с проверкой суммы ровно на пороге.
3. Раскройте **Только оформление и комментарии**. У `labels.json` указано **Только форматирование JSON**, а у `states.ts` — **Правки обычных комментариев**. Нажмите на любой из них, чтобы открыть исходный diff.
4. В группе **К просмотру** найдите изменение числа в `checkout.json`, директиву линтера в `audit.ts` и файл формата `.rules`.
5. Раскройте **Прочее** и откройте `manual.md`. Расширение `.md` определяет эту группу, хотя файл находится в `tests/`.

Если `fixtures/example.json` недоступен или повреждён, приложение показывает ошибку. После восстановления файла можно повторить открытие без перезапуска.

## Подключение GitLab

1. В GitLab создайте legacy Personal Access Token с правом `read_api` или fine-grained токен с правами **User → User → Read** и **Merge Request → Read** для проекта из ссылки на MR. [Права GitLab REST API](https://docs.gitlab.com/auth/tokens/fine_grained_access_tokens_rest/)
2. В приложении нажмите **GitLab**. В поле **Адрес сервиса** введите основной HTTPS-адрес вашей установки, например `https://gitlab.example.com`, и токен. При необходимости включите VPN.
3. Нажмите **Подключить**. Приложение проверит токен через `/api/v4/user` и покажет имя пользователя.
4. Перезапустите приложение и снова откройте **GitLab**, чтобы проверить сохранение.
5. Нажмите **Отключить**, чтобы удалить токен из Связки ключей. Для замены токена введите новый и нажмите **Обновить подключение**.

В поле **Ссылка на ревью** вставьте ссылку на MR с подключённого GitLab и нажмите **Открыть**. Выберите файл слева, чтобы увидеть diff. Приложение показывает предупреждение о неполных данных, когда GitLab сообщил об ограничении или вернул неполный diff. [GitLab Merge Requests API](https://docs.gitlab.com/api/merge_requests/#list-merge-request-diffs)

Токен хранится как пароль в Связке ключей macOS. Основной процесс отправляет его на указанный HTTPS-адрес, а при перенаправлении останавливается. Если сохранить токен не удалось, кнопка **Только до выхода** позволяет держать его в памяти. Интерфейс показывает, какой режим действует.

Для сборки локального помощника Связки ключей на macOS используются Xcode Command Line Tools. Приложение собирает его при запуске и сохраняет в `.local/bin/`.

## Подключение GitHub

1. Создайте **Fine-grained personal access token**. Выберите тестовый репозиторий и установите **Pull requests → Read-only**. [Права GitHub API](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files)
2. Нажмите **GitHub**, введите токен и нажмите **Подключить**. Приложение покажет имя пользователя.
3. В том же окне GitHub вставьте ссылку вида `https://github.com/owner/repo/pull/123` и нажмите **Открыть**. Поле видно до подключения. Выберите файл, чтобы увидеть diff.
4. При неполных данных приложение показывает предупреждение. Файлы, для которых GitHub не вернул текстовый diff, видны в списке.

GitHub-токен хранится в отдельной записи Связки ключей `local.review-assistance.github`. Кнопка **Отключить** удаляет эту запись. Режим **Только до выхода** хранит токен в памяти. Запросы с токеном GitHub идут на `https://api.github.com`.

## Группировка файлов

`md`, `txt`, `png`, `jpg`, `jpeg`, `tiff`, `log` и `pdf` попадают в **Прочее** по расширению. Из остальных файлов те, в чьём пути есть подстрока `spec` или `test`, попадают в **Тесты**. Регистр букв не влияет на совпадение. **К просмотру** и **Тесты** раскрыты при открытии ревью. **Прочее** и **Только оформление и комментарии** свёрнуты.

Для оставшихся файлов фильтр сравнивает разобранные токены JSON и синтаксис JavaScript и TypeScript. Обычные комментарии проверяются отдельно от кода. Для JavaScript и TypeScript нужен diff с достаточным контекстом от начала файла. Изменения кода, директивы инструментов и сомнительные случаи остаются в списке **К просмотру**.

Фильтры подключаются в одном модуле. Они возвращают результат проверки и причину. Экран решает, в каком списке показать файл. [Модуль фильтров](src/review/review-filters.module.ts) · [Контракт фильтра](src/review/domain/file-filter.ts)

Команда `npm test` проверяет правила и подключает дополнительный фильтр в тесте.

## Блок 4а «Языки репозитория»

Блок расширяет фильтрацию из блока 4 для GitLab. Подключение GitHub к тому же фильтру запланировано на блок 8. Для GitHub, локального примера и ревью без статистики языков действует сортировка блока 4.

При первом открытии MR репозитория GitLab приложение запрашивает статистику языков. Для этого запроса fine-grained токену GitLab требуется **Project → Read** для этого проекта. [Права GitLab REST API](https://docs.gitlab.com/auth/tokens/fine_grained_access_tokens_rest/#project)

| Площадка | Запрос |
| --- | --- |
| GitLab | `GET /api/v4/projects/:id/languages` |
| GitHub, блок 8 | `GET /repos/{owner}/{repo}/languages` |

Приложение учитывает все языки из ответа, включая языки с малой долей. Успешный результат сохраняется в локальном профиле приложения по хосту и репозиторию. При открытии другого MR того же репозитория используется кэш.

Отдельный фильтр распознавания языка возвращает результат и причину через общий интерфейс. Экран применяет правила по порядку. Каждому файлу соответствует первое подходящее правило.

1. Применить действующие специальные правила. Файл, у которого весь diff прошёл фильтр оформления и комментариев, попадает в **Только оформление и комментарии**. Правила для специальных расширений сохраняют приоритет.
2. Распознанный тест попадает в **Тесты**.
3. Файл попадает в **Основное**, если его распознанный язык входит в список языков репозитория. Например, `.ts` и `.tsx` распознаются как TypeScript.
4. Остальные файлы попадают в **Остальное**. Это касается и кода на языке, которого ещё нет в статистике площадки.

Каждый файл показывается один раз. В **Остальном** рядом с файлом видна причина. Любой файл можно открыть и посмотреть его исходный diff.

При пустом списке, ошибке запроса или отказе в доступе приложение использует сортировку блока 4 и показывает пояснение. Пустой успешный ответ сохраняется в кэше. После ошибки приложение повторяет запрос при следующем открытии ревью.

#### Проверка без сети

Подставить ответ со списком Go и TypeScript.

| Изменение | Ожидаемая группа |
| --- | --- |
| `service.go` с изменением логики | **Основное** |
| `service_test.go` с новым тестом | **Тесты** |
| Файл `.ts` с одними отступами | **Только оформление и комментарии** |
| `config.yaml` с изменением значения | **Остальное**, причина **YAML отсутствует в списке языков репозитория** |

Открыть второй MR того же репозитория и проверить, что запрос языков выполнен один раз. Отдельно проверить возврат к сортировке блока 4 при пустом ответе, ошибке запроса и отказе в доступе.

## Блок 5 «Порядок чтения»

Откройте пример. Нажмите **Дальше** три раза, чтобы пройти от `delivery.controller.ts` через `delivery.ts` и `delivery.repository.ts` к `delivery.test.ts`. Рядом с кнопкой видна позиция в очереди. На последнем файле кнопка выключается.

Очередь строится локально по путям и относительным импортам JavaScript и TypeScript, видимым в diff. В ревью по ссылке **Дальше** идёт по списку слева сверху вниз. Сначала идут все файлы из **Основного** или **К просмотру**, затем **Тесты**, затем остальные группы. Порядок внутри группы учитывает найденные связи между файлами. Каждый файл входит в очередь один раз. Можно выбрать любой файл слева и продолжить с него.

## Логи

При запуске через `npm run start:dev` логи появляются в том же терминале. В них видны запуск и закрытие окна, подключения, операции со Связкой ключей, загрузка MR и PR, страницы diff и ошибки. Для запросов указываются сервис, операция, HTTP-статус и время. Для сетевых ошибок по возможности указывается код причины. При отказе GitLab в доступе к профилю или MR приложение отдельно распознаёт известный код нехватки прав и HTML-ответ. Код 429 означает ограничение частоты запросов.

Чтобы увидеть языки, по которым группируются файлы GitLab MR, запусти `REVIEW_ASSISTANCE_DEBUG=1 npm run start:dev` и открой MR. В терминале появится строка `[GitLabRepositoryLanguages] languages=["Go","TypeScript"]`. Она выводится и при чтении из кэша. Пустой список отображается как `languages=[]`.

Токены, ссылки, имена аккаунтов, пути к файлам из ревью и содержимое diff в эти логи не записываются.

## Архитектура

NestJS работает внутри основного процесса Electron. Общая точка входа запускает и закрывает контекст. AppModule подключает модули окна и ревью и регистрирует адаптер между ними. [main.ts](src/main.ts) · [AppModule](src/app.module.ts)

- DesktopModule управляет окном Electron. AppModule передаёт ему пути к странице и preload. [DesktopModule](src/desktop/desktop.module.ts)
- ReviewModule связывает прикладной сервис с источником данных через интерфейс. Адаптер источника читает локальный JSON и разбирает unified diff. [ReviewModule](src/review/review.module.ts) · [Прикладной сервис](src/review/application/open-example-review.ts) · [Адаптер источника](src/review/infrastructure/json-example-review.source.ts)
- Домен описывает MR, файлы и строки diff. Он проверяет уникальность путей и наличие изменений, подсчитывает добавленные и удалённые строки. [Домен ревью](src/review/domain/review.ts)
- Слой представления отображает diff. Кнопка «Открыть пример» отправляет запрос через preload. Адаптер IPC проверяет, что запрос пришёл из основного окна, и вызывает прикладной сервис. [Код представления](src/presentation/review/) · [Обработчик IPC](src/presentation/review/review-ipc.handler.ts)
- Модули GitLab и GitHub используют общий сервис подключения и отдельные записи Связки ключей. Каждый модуль подключает свой адаптер загрузки ревью. [GitLabModule](src/gitlab/gitlab.module.ts) · [GitHubModule](src/github/github.module.ts)
